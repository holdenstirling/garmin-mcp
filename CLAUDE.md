# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal remote MCP server (streamable HTTP + MCP OAuth 2.1, GitHub as the identity provider) that gives claude.ai read access to Garmin Connect via the **unofficial** `garminconnect` library. It runs on a single GCP VM behind Caddy (optionally behind Cloudflare). README.md has the full setup, deploy, and re-auth runbook.

## Commands

```bash
uv sync                                        # Python 3.12, deps pinned exactly in pyproject + uv.lock
uv run pytest                                  # all tests (Garmin and GitHub are mocked)
uv run pytest tests/test_registry.py           # one file
uv run pytest tests/test_auth.py::test_full_flow_and_tool_call   # one test
uv run pip-audit                               # dependency audit (dev group)

# Local server without OAuth (refused unless PUBLIC_BASE_URL is localhost and HOST is 127.0.0.1)
export GARMIN_MCP_FERNET_KEY=$(uv run python -c 'from garmin_mcp.tokens import generate_key; print(generate_key())')
export PUBLIC_BASE_URL=http://localhost:8000 DATA_DIR=./data
DEV_NO_AUTH_USER=holden uv run garmin-mcp       # then MCP Inspector -> Streamable HTTP -> http://localhost:8000/mcp

cd web && bun install && bun run build   # Rabbit frontend -> src/garmin_mcp/web_dist (gitignored)
./deploy.sh --rabbit     # Rabbit web app only (separate rabbit.service; never restarts the MCP server)
./deploy.sh              # MCP server: uploads working tree over IAP, uv sync --frozen, switch release, restart, health check
./deploy.sh --rollback   # previous release
uv lock                  # only when dependencies change; deploy refuses without uv.lock
```

There is no linter/formatter configured. `scripts/smoke_live.py` hits the real Garmin account and is run on the VM only, never in CI.

## Architecture

Request path: `server.py` (MCPServer tools) → `tools.GarminService` (transport-independent; this is what unit tests target) → `registry.Registry` (validate method + args) → `GarminProvider.get_client(user_id)` → `GarminSession.call(fn, kwargs, retry=...)` → `shaping.shape()` on the result.

- **Three tools only**: `search`, `execute`, `recent_activities`. `execute` is a generic dispatcher over the whole `garminconnect.Garmin` class rather than one hand-written tool per endpoint.
- **Registry security model** (`registry.py`, see its module docstring). The method index is built at startup by introspecting `vars(Garmin)`, and dispatch stores the *unbound function object*, so nothing does `getattr` on user input. Classification is default-deny: READ requires a `get_`/`count_` prefix **and** source with no POST/PUT/DELETE/PATCH; WRITE requires an explicit write prefix; everything else is BLOCKED. Path-like params, variadic signatures, binary returns, and `ALWAYS_BLOCKED` (login, raw `connectapi`, GraphQL, file uploads) can never be called. Writes also need `GARMIN_ALLOW_WRITES=true`. Keep this posture when changing the registry. Upgrading `garminconnect` changes the method surface, so re-check classification.
- **Provider abstraction** (`providers/base.py`): tools depend only on `GarminProvider`/`GarminSession` and the `GarminError` hierarchy. `GarminError` messages are shown to the MCP caller; any other exception becomes a generic `Internal error (TypeName)` in `server.run()`. `providers/official.py` is a stub for a future swap via `server.create_app`.
- **Unofficial provider** (`providers/unofficial.py`): tokens are passed to garminconnect as an inline JSON blob, never as a tokenstore path, so the library never writes plaintext. After each call, refreshed tokens are diffed against the last persisted copy and written back through `EncryptedFileTokenStore`. Cloudflare challenges are detected by instrumenting the requests session and are surfaced as `CloudflareBlocked`, which is distinct from `ReauthRequired`. Optional TLS impersonation exists for the datacenter-IP 403 problem.
- **Login is never automatic.** `login_start`/`login_complete` run only from `garmin-mcp-login` (`login_cli.py`), interactively, with one attempt. Garmin rate-limits logins per IP and fingerprint, so don't add retries or automatic re-login. `ReauthRequired` tells the user to re-run the CLI on the server.
- **Auth** (`auth.py`, see its docstring for the flow): the server is its own OAuth AS (DCR limited to allowlisted redirect URIs, PKCE, RFC 8707 resource check) and delegates identity to GitHub. The GitHub token is used once to read the numeric user ID and then discarded. `ALLOWED_GITHUB_USERS` maps `<numeric_github_id>:<user_id>`, using numeric IDs because logins can be re-registered. Access tokens and pending auths live in memory; clients and refresh-token hashes persist in a Fernet-encrypted state file. `server.current_user()` re-checks the token's `user_id` claim against the allowlist on every call.
- **Per-user isolation**: tokens, `TTLCache` entries, and `RateLimiter` buckets are all keyed by `user_id`. Writes and `ReauthRequired` clear that user's cache.
- **Secrets** (`secrets.py`): Secret Manager in production, with env-var fallback (`GARMIN_MCP_FERNET_KEY`, `GITHUB_CLIENT_SECRET`) for local use.
- **Config**: `config.Settings.from_env()`. Every variable is documented in `.env.example`. `PUBLIC_BASE_URL` must be a bare https origin (localhost excepted) and derives the issuer, `/mcp`, and `/github/callback` URLs.
- **Poller** (`poller.py`, optional, on when `POLL_USER_ID` is set): a daemon thread started in the app lifespan (`server._attach_poller`) that polls `get_activities` via `GarminService.read_uncached` (bypasses the TTL cache, still rate-limited and on the shared session lock) and fires a Claude Code routine. Delivery is deliberately at-most-once: the cursor advances only on 200, but also on unknown outcomes (`pending_through` marks a fire in flight), since `/fire` has no idempotency key. Keep that invariant. It must stay in-process: Garmin rotates the refresh token, so a second process could race the server's refresh.
- **Rabbit web app** (`webapp.py`, `webauth.py`, `webpush.py`, `appstore.py`, frontend in `web/`; off unless `APP_ENABLED`; plan in `docs/plans/web-app.md`): in production it runs as a separate process (`rabbit.service`, :8001, own user/data dir/Fernet key, `MCP_ENABLED=false` so `server.build_web_only_app` mounts no `/mcp`); Caddy routes `/app*` to it. Keep it that way so app work can't take down the connector, and never let two processes hold the same user's Garmin tokens. In one-process mode the `/app` routes are appended to the MCP Starlette app, and web-app config errors only disable `/app`. Google sign-in (state cookie + PKCE, userinfo read once, `sub` pinned to user_id on first login) issues an opaque `__Host-` session cookie whose hash is stored encrypted. Every `/app/api` call goes through `webapp._api`: Host check, user_id from the session only (never from the body or tool args), and Origin + JSON content-type on mutating calls. Web Push endpoints are allowlisted push-service hosts (SSRF guard). The app sets its own CSP on static files. The frontend is a Vite + React port of Dolly's UI (`web-mcp`); keep its tokens in `web/src/styles/globals.css`.
- **TrainingPeaks** (`trainingpeaks.py`, off unless `TRAININGPEAKS_ENABLED`): four extra MCP tools (`tp_workouts`, `tp_create_workout`, `tp_delete_workout`, `tp_upload_garmin_activity`) registered in `build_app` only when a `TrainingPeaksService` is passed. Unofficial `tpapi.trainingpeaks.com`: the `Production_tpAuth` cookie is stored per user with `EncryptedFileTokenStore` in `$DATA_DIR/trainingpeaks` by `garmin-mcp-trainingpeaks-login` (never automatic), exchanged for an in-memory bearer at `/users/v3/token`. Only fixed endpoint paths are built (no caller-supplied paths), writes need `TRAININGPEAKS_ALLOW_WRITES`, and deletes refuse workouts with completed data. Errors subclass `GarminError` so their messages reach the caller. Garmin FIT download for uploads goes through `GarminService.activity_original_file`, internal only; `execute` still blocks binary methods. Tests: `tests/test_trainingpeaks.py` (MockTransport, no network).
- **Plan builder** (`planbuilder.py` pure generator and Garmin workout JSON, `plans.py` `PlanService`, routes under `/app/api/plan*`, frontend in `web/src/components/plan/`): the setup wizard saves athlete + goal fields and builds a periodized plan (base/build/peak/taper/race, recovery every 4th week) stored in the `plan-<goal_id>` doc; `goal.plan_source = "builder"` makes `weekplan` read it directly instead of asking the model. Session edits keep `edited`/`title_custom`. Garmin sync is user-triggered only: it uploads and schedules sessions in a 7/14/28-day window via `GarminService.workout_upload/schedule/delete` (fixed garminconnect methods, internal only, not exposed through `execute`), compares a per-session hash so unchanged workouts aren't re-uploaded, and deletes replaced ones (`garmin_orphans`). Workout names start with `Rabbit: `. Tests: `tests/test_plans.py`.
- **Events** (`events.py` `EventStore`, `/app/api/events*`, frontend `web/src/components/events/`): every race on the athlete's calendar in the encrypted `events` doc. The active goal points at the main event (`goal.event_id`); making another event main re-points the goal in place (same coach log). Other events are passed to `build_plan(events=...)` and placed by `planbuilder.apply_events` as B/C race days; `plans.get` flags `events_changed` (signature mismatch) so the app can offer a rebuild. "Look up" (`Agent.lookup_event` -> `AnthropicBackend.research`, server-side web search) returns JSON that `events.clean_info` reduces to known short string fields and https links; it's capped at `LOOKUPS_PER_DAY` per user and always shown as "found online". The coach context lists upcoming events.
- **Stats** (`stats.py`, `GET /app/api/stats`, `web/src/components/stats/`): pure `compute()` over a year of compact activities (one cached Garmin read, result cached 5 min per user): day and active-week streaks, totals, 12-week volume, 26-week calendar, sports, bests, badges, and plan adherence via `weekplan.merge` against the built plan. Sport-agnostic; multisport legs count once.
- **Human coaches** (`coaches.py`, `/app/api/coaches*`, `/app/api/coachchat*`, `/app/api/coach/athletes/{id}/*`, frontend `web/src/components/coach/`): the athlete invites a coach by email (global `coach_links` doc). `WebAuth` lets a verified Google email sign in while some athlete links it (`coach_<sha256>` user id unless the email is an allowlisted athlete) and re-checks on every request, so removing the coach revokes access. Every coach route calls `links.require(coach, athlete, perm=...)`; `can_edit_plan` gates session edits and `can_see_rabbit_chats` (off by default) gates the read-only Rabbit transcript. Athlete<->coach threads (general or per planned session) live in the athlete's `coach_chat` doc; coach notes in `coach_notes`, and shared ones go into Rabbit's context.
- **Google Calendar + travel** (`gcalendar.py`, `WebAuth.start_calendar`, `/app/api/calendar`, `PlanService.add_travel/remove_travel`): connecting reuses Rabbit's Google OAuth client and callback (pending `kind="calendar"`, must be the same signed-in user), asks only for `calendar.readonly` with offline access, and stores the refresh token in the encrypted `gcal` doc. `summarize()` turns primary-calendar events into busy minutes per day and travel windows (multi-day all-day events or travel words). Travel mode rewrites sessions on days away (bike/swim/brick swapped by what's available, 75-min cap, long sessions moved to the nearest home day that week), keeps the originals on the trip for undo, and orphans any synced Garmin workouts it replaces. The update script enables the Calendar API.
- **Oura** (`oura.py`, `/app/auth/oura/*`, `/app/api/oura`; on when `OURA_CLIENT_ID` is set and the `garmin-mcp-oura-client-secret` secret exists, see `infra/cloudshell/8-oura.sh`): OAuth2 with Oura's API v2; tokens (rotating refresh) in the encrypted `oura` doc. Oura's API agreement 4(d) forbids feeding Oura API data to an AI model except via Oura's own MCP server, so Oura data is only shown in the app and used by deterministic rules. Never add it to `context_block`, tool results or anything the model reads.
- **Load + adjustments** (`load.py`, `adjust.py`, `/app/api/load`, `/app/api/plan/adjust`): fitness/fatigue/form use one TSS-like scale for history (HR-based IF when threshold HR is known) and plan forecast (IF by session kind). `adjust.propose` is deterministic (so Oura data may feed it): low recovery eases the next 3 days, a missed long session comes back shortened on a free day, a mostly-missed week makes next week 15% lighter. Applying re-computes the proposal server-side and requires the same id (409 otherwise); dismissals are remembered per proposal id.
- **Race support** (`strength.py`, `nutrition.py`, `racepack.py`, debriefs in `Agent.debrief`, `share.py`): builder adds phase/sport strength routines, prehab from injury notes (general, labelled not a diagnosis) and weekly mobility; `public_plan` attaches fueling (gut-training ramp to race-day g/h). `/app/api/racepack` builds pacing by leg from FTP/threshold pace/CSS/LTHR, fueling, gear, altitude/Hope Pass notes and an Open-Meteo forecast within 14 days. `/app/api/events/{id}/debrief` forces a structured tool call over the race's Garmin activity and the athlete's notes; learnings from the last two debriefs go into the coach context. `/app/s/<token>` is a server-rendered, escaped, noindex read-only page (one revocable token per athlete; no chats or health data).
- **Profile + race fit** (`coaching.validate_athlete`, `profilephoto.py`, `racefit.py`, `Agent.race_strategy`, frontend `components/plan/{ProfileScreen,ProfileFields,GoalsTab,PhotoField}.tsx`, `components/events/RaceFitScreen.tsx`): athlete traits (home/elevation, years training, strengths/limiters, heat/sweat, altitude, terrain access, race history, motivation, season goal) are bounded in `validate_athlete` and go into `context_block` compactly. Profile photo: raw-body `POST /app/api/profile/photo` (client resizes to 256x256 JPEG, ≤300 KB, magic bytes checked: JPEG/PNG/WebP), Fernet-encrypted `photo` doc (version in `photo-meta`, exposed as `/me.photo`), served to the owner and to linked coaches via `/app/api/coach/athletes/{id}/photo` with `?v=` cache busting, `private` caching and `nosniff`. `racefit.analyze` is deterministic (altitude from `event.elevation_m`, known places or altitude text but never the climbing total; climbing per km; heat/cold; trail; open water; duration vs experience; night) and returns factors `helps|neutral|watch|risk`. `GET/POST /app/api/events/{id}/strategy` returns fresh race fit + the stored strategy + the coach's shared race notes; POST forces one `save_race_strategy` tool call (5/day per user) and stores it on `event.strategy` (coach-private like debriefs). Coach notes take an optional `event_id` (checked against the athlete's events) and show in that race's view and, prefixed with the race name, in Rabbit's context. Body weight only appears as neutral power-to-weight; no weight-loss advice. Oura data never feeds any of this.
- **Gamification** (`progress.py`, `/app/api/progress`, `/app/api/progress/seen`, frontend `components/progress/`): XP is a per-user ledger (`progress` doc) keyed by activity id, plan goal id, badge and quest, so XP only rises and nothing counts twice; the first read back-fills the last year without celebrating it. Workouts 10 + 1/2 min (3 h cap), planned session +15, perfect plan week +100, badge +100, quests their own XP. Levels: total XP for level L is 50·L·(L-1), rabbit-themed tier names. The day streak (`stats._streaks`) is kept by training, by plan rest days, and by one free rest day per Monday-start week; only trained days count. Stats shows level/streak/week, recovery, fitness and form, plan week, the 12-week trend and the next 3 badges; the rest is behind "More stats".
- **Gear garage** (`gear.py` `GearStore`, `/app/api/gear*`, frontend `web/src/components/gear/`): shoes, bikes, wetsuits etc. in the encrypted `gear` doc (≤60 items, validated enums/lengths; `GearError` is a `CoachError`, so `_plan_call` makes it a 400). Mileage is computed, not stored: `start_km` + activities since `added` (until `retired_on`) that are tagged (`activity_ids`) or untagged in a `default_for` sport (one default per sport per kind), from `StatsService.activities` only; Garmin-imported items (`garmin_uuid`) prefer `get_gear_stats` totals. Status `soon` at 80% of `alert_km`, `retire` at 100%. Import uses `GarminService.gear_list` (fixed read-only `get_gear`/`get_gear_defaults` with the client's `profile_id`), matched by uuid. +25 XP per item via `Progress.update(bonus=...)`, optional `gear` quest; `racepack.build(gear=...)` adds `your_gear` with worn/new-shoe warnings.
- **Poll schedule** (`poller.Schedule`): every `POLL_FAST_MINUTES` in `POLL_FAST_HOURS` (5-9), every `POLL_DAY_MINUTES` in `POLL_DAY_HOURS` (default 6-22, end hour inclusive), hourly overnight; local time per user in Rabbit.
- **Live sync** (`sync.py` `LiveSync`, `POST /app/api/sync`): one uncached `get_activities` (limit 5) per user per 45 s (in-memory throttle; inside the window the last result comes back with `changed: false`). Its cursor is the encrypted `sync` doc, never the poller's state; the first call is a baseline. New ids call `StatsService.invalidate(uid, activities=True)` (drops cached stats, the year of activities and the user's Garmin TTL cache, so XP/streak/load/gear mileage re-read). `Proactive.poll` does the same when the poller reports new activities. Garmin errors come back as `{error}` with 200. The app syncs on open, on visibility and every 60 s on home, then refreshes progress/week/Today and toasts the XP gained.
- **Today card** (`today.py`, `GET /app/api/today`, `web/src/components/today/TodayCard.tsx`): deterministic `recommend()` (priority order in the module docstring: race > adjustment > done > low recovery > planned > plan rest > nothing planned). Oura readiness is used here deterministically only and never reaches the model. It replaces the home race-soon and adjust banners.
- **Weekly recap** (`recap.py`, `GET /app/api/recap?week=`, `web/src/components/recap/RecapSheet.tsx`): Monday-start week, last 8 weeks. XP comes from the progress ledger's `xp_by_week` (last 26 weeks) and badges from `badge_dates`; back-fill records neither non-workout XP nor badge dates. `Proactive._maybe_recap` pushes Sundays at `recap_time` (default 18:00, `recap_enabled` setting) to `/app/?open=recap`, claimed once per week like the brief, with no model call.
- **Workout day** (`workoutday.py`, `GET /app/api/workout/today?session_id=`, `GET /app/api/workout/reaction?activity_id=`, frontend `web/src/components/workout/`): deterministic, no model. Pre-workout: today's (or the chosen) built-plan session with purpose by kind/phase, warm-up/main/cool-down steps with targets in the athlete's units (pace from threshold pace, power from FTP, swim from CSS, HR from threshold HR, else RPE), key cue, `nutrition.fuel`, default gear with mileage, Garmin sync state (send uses `/plan/garmin/sync` 7 days), Open-Meteo weather at `home_location` (cached 30 min in-process) and a readiness line from `today.recommend` (Oura shown only). Rest days and no plan get a rest card or a free 30-45' suggestion. Reaction: matched like `weekplan.merge` -> `nailed` (±10% time, not out of zone) / `close` / `different` / `bonus`, XP (`workout_xp` + plan bonus, display only; the ledger still awards), streak, new 12-month bests, gear km, tomorrow. The app opens it once per new synced activity (ids in localStorage); `onCheckIn` props are for the voice check-in. Tests: `tests/test_workoutday.py`.
- **Explore races** (`explore.py`, `/app/api/explore*`, frontend `web/src/components/explore/`): RunSignup's public race search (no key), one request per selected RunSignup event type (≤4, concurrent), merged/deduped/sorted, normalized to plain text (description HTML stripped server-side; the UI renders text only), cached 6 h in a bounded in-memory LRU; upstream trouble is a friendly 502. `fit_hints` are deterministic hints vs the main event (same distance, tune-up, too close, B-race, altitude from `racefit.KNOWN_PLACES`). "Find more with Rabbit" (`POST /explore/ai`) is `research` + a `report_races` tool, filters only in the prompt (no athlete or Oura data), 5/day per user on cache misses, cached 24 h per query, marked `source: "web"`. `POST /explore/add` maps a race + chosen distance to `EventStore.create` (priority C, "Found in Explore"). Tests: `tests/test_explore.py` (MockTransport).
- **Voice check-ins** (`checkins.py` `CheckinStore`, `Agent.checkin`, `/app/api/checkins*`, frontend `web/src/components/checkin/`): the athlete talks (Web Speech API, typed SpeechRecognition in `web/src/lib/speech.ts`, textarea fallback) or types how a session felt; one forced `save_checkin` tool call fills a fixed schema (feel, RPE, sleep, energy, soreness by area/side/level, pain flag, mood, tags, summary) strictly from the text, with the deterministic `fallback_parse` when there's no model or it fails, and `clean` validates everything. 20/day, newest 120 kept in the encrypted `checkins` doc. Used by `adjust.propose` (pain flag in 3 days eases the next 3 days with a see-a-professional tip; soreness 3 or two rough check-ins -> one easy day), `today.recommend` (rough check-in today/yesterday -> `easy`), `context_block` (last 3 summaries; athlete-entered, never Oura), the linked coach's overview (last 5 summaries) and progress (+10 XP once per day via bonus key `checkin:<date>`). `VoiceCheckIn` is exported for other screens (portals to body so it can open inside another sheet).
- **Oura apps** must be created at developer.ouraring.com (the old cloud.ouraring.com/oauth/applications page only edits existing apps). Refresh tokens are single use: `OuraClient.access_token` serializes refreshes per user and re-reads inside the lock.
- **Logging**: use `logs.log_event(logger, level, event, **fields)`, which emits JSON lines. Never log tokens, passwords, or response payloads.

## Library notes

- `mcp==2.2.0` uses `mcp.server.mcpserver.MCPServer`, not the older `FastMCP` API. The app runs stateless with JSON responses and DNS-rebinding protection (allowed hosts/origins are set in `build_app`).
- The HTTP client is `httpx2`, not `httpx`.
- Async tests don't use pytest-asyncio. `tests/test_auth.py` wraps them with a local `@run` decorator (`anyio.run` inside the app lifespan) and drives the real ASGI app through `httpx2.ASGITransport` with GitHub mocked by `MockTransport`.
- Shared fakes are in `tests/conftest.py`. `FakeGarmin` includes deliberately dangerous methods (`get_sneaky`, `get_file`, `connectapi`, ...) to exercise registry blocking. `make_service()` builds a `GarminService` around the fakes.
