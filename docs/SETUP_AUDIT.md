# Setup audit: Rabbit + Garmin MCP on GCP

Scope: one e2-micro VM `garmin-mcp` (project `training-project-511604`, `us-central1-a`, 34.45.18.209) running Caddy, `garmin-mcp.service` (:8000) and `rabbit.service` (:8001), deployed from Cloud Shell over IAP SSH. Written 2026-10-14 from the repo only (`deploy.sh`, `infra/`, `src/garmin_mcp/{config,server,secrets,appstore,logs,legal,auth,webauth}.py`).

"Check live" means the code can't settle it. Run `bash infra/cloudshell/9-audit.sh` from Cloud Shell to check (read-only, prints PASS/WARN/FAIL).

Effort: S = under 30 min, M = a few hours, L = a day or more.

## Priority 1: fix now

| # | Item | Risk | Evidence | Fix | Effort |
|---|---|---|---|---|---|
| 1 | **No backups** | Disk loss, a bad deploy or `rm` wipes every user's data with no restore. Rabbit is a multi-user app, so this hits other people too. | `setup.sh` creates the VM without `--resource-policies`, and no script creates a snapshot schedule. All state is under `/var/lib/{garmin-mcp,rabbit}` on the boot disk. | `bash infra/cloudshell/10-backups.sh` (daily 09:00 UTC, 14-day retention, keeps snapshots if the disk is deleted). Test a restore once: create a disk from a snapshot, attach it to a throwaway VM, and check the data decrypts with the Secret Manager keys. Then `bash infra/cloudshell/14-offsite-backups.sh` (done in-repo): a nightly `tar` of both data dirs to `gs://<project>-rabbit-backups` (versioned, 30 daily + 12 monthly, VM may only create objects), so a backup survives losing the VM and its snapshots. Restore steps: `infra/restore-backup.md`. | S |
| 2 | **Backups only work if the Fernet keys survive** | Snapshots hold ciphertext. If a Fernet key version is destroyed, every snapshot of that data is unreadable. | `secrets.get_secret` always reads `versions/latest`. `tokens.py` uses one `Fernet` (no `MultiFernet`). | Never `destroy` or `disable` versions of `garmin-mcp-fernet-key` / `garmin-mcp-rabbit-fernet-key`. Restrict `secretmanager.admin` to you. Keep an offline copy of both keys, for example in a password manager. | S |
| 3 | **No monitoring or alerting** | Outages, cert renewal failures, a full disk or an OOM-killed service go unnoticed until a user complains. | No uptime check, alert policy or Ops Agent anywhere in `infra/`. The only health check is the post-deploy curl in `deploy.sh`. | Create a Cloud Monitoring uptime check on `https://<host>/healthz` (MCP) and `https://<host>/app/privacy` (Rabbit, because Caddy only sends `/app*` to :8001) with an email alert. Add an alert on the VM's `disk/percent_used`. Uptime checks are free at this volume. | S |
| 4 | **No cost guardrails** | A leaked key, runaway agent loop or egress spike bills without a ceiling. | No budget in `setup.sh`. Anthropic limits are per user only: `AGENT_DAILY_TOKEN_BUDGET=2000000` per user per day (cached input counted), with `AGENT_PROACTIVE_MODEL=claude-haiku-5-5` (the default since Oct 2026) and `AGENT_DAILY_MESSAGES=40` chat messages per user per day. There's no global cap, so N users means N × 2M tokens a day. | Set a GCP budget on the billing account (for example $10/month, alerts at 50/90/100%). In the Anthropic console, put Rabbit's key in its own workspace with a monthly spend limit and usage alerts. Consider a global daily token cap in `agent.py`. | S |
| 5 | **Deploys depend on a hand-run, ephemeral Cloud Shell** | Untested or uncommitted code can ship. Every deploy needs an interactive `gcloud auth`. There's no audit trail of what is running. | `7-update-rabbit.sh` runs `git pull --ff-only \|\| true` (a failed pull still deploys the stale tree). Tests run only `if command -v uv` (silently skipped in a fresh Cloud Shell without uv) and can be bypassed with `SKIP_TESTS=1`. `deploy.sh` tars the *working tree*, including untracked files. The release name uses `nogit` if git is missing. | Add a GitHub Actions workflow: on push to `main`, run `uv sync --frozen && uv run pytest && uv run pip-audit` plus the web build, then deploy via **Workload Identity Federation** (no JSON keys) as a `deploy@` service account. Give that account `roles/iap.tunnelResourceAccessor` and `roles/compute.osAdminLogin` **on the instance only** (this is root on the VM, so protect `main` with required reviews). Until then, make `7-update-rabbit.sh` fail on a failed pull and when uv is missing. | M |

## Priority 2: soon

| # | Item | Risk | Evidence | Fix | Effort |
|---|---|---|---|---|---|
| 6 | **Google OAuth "Testing" mode** (check live) | In Testing mode, refresh tokens for apps with non-basic scopes expire after **7 days**, and the app is capped at 100 test users. `calendar.readonly` is a *sensitive* scope, so Calendar connections silently die every week. Sign-in itself is fine: Rabbit issues its own 90-day session (`APP_SESSION_TTL_SECONDS=7776000`). | `gcalendar.py` uses `SCOPE=.../calendar.readonly`. `webauth.py` requests `access_type=offline, prompt=consent`. | Publish the consent screen ("In production"). Sensitive scopes need Google verification: a privacy policy URL on a domain you own (`rabbit.holdenottolini.com/app/privacy`), a homepage and a demo video. That's easier after the domain move. If you stay in Testing, show "reconnect Calendar" when a refresh fails. | M |
| 7 | **Single VM is a single point of failure, with tight memory** | Any VM, zone or host failure means full downtime. On 1 GB RAM, `garmin-mcp.service` has **no** `MemoryMax`, so a leak there can still take down the whole box. | `MACHINE_TYPE=e2-micro`, `DISK_SIZE=30GB` pd-standard (free tier). `rabbit.service` has `MemoryHigh=300M/MemoryMax=400M`. 1G swapfile. | Acceptable for a personal app, as long as items 1 and 3 are fixed. Add `MemoryMax=450M` to `garmin-mcp.service`. Turn on deletion protection (`gcloud compute instances update garmin-mcp --deletion-protection`). Write a 10-line restore runbook: snapshot to disk to VM, reattach the static IP, and nothing else changes. If Rabbit grows, move to e2-small (about $12/month) before considering more VMs. | S |
| 8 | **OS updates: security-only, no reboot** | Kernel and libc fixes install but don't take effect without a reboot. Caddy, uv-managed Python and the uv binary are never auto-updated. | `bootstrap-vm.sh` installs and enables `unattended-upgrades` (Debian default: security origin only, `Automatic-Reboot=false`). Caddy comes from the Cloudsmith repo, which isn't in the allowed origins. Python comes from `uv python install 3.12`. | Set `Unattended-Upgrade::Automatic-Reboot "true"` with `Automatic-Reboot-Time "10:00"` (UTC, about 4am Denver) and accept around 30 s of downtime. Add Caddy's origin to `Origins-Pattern`, or run `apt upgrade caddy` monthly. Bump `UV_VERSION` and Python minor releases occasionally. Check live: pending updates, running vs installed kernel. | S |
| 9 | **Shared VM service account across both processes** | The rabbit and garmin-mcp processes can each fetch *both* Fernet keys from the metadata server. So "Separate Fernet key ... this process can't decrypt its files" (`rabbit.env.example`) holds for the filesystem but not for Secret Manager: a code-execution bug in Rabbit exposes MCP data. | `setup.sh` binds `secretAccessor` for every secret to the single `garmin-mcp-vm` SA. `8-oura.sh` does the same. | Accept it and fix the comment, or isolate properly. One option is to load secrets as root in `ExecStartPre` and pass them through `LoadCredential=`, then block metadata server access (169.254.169.254) per unit with `IPAddressDeny=169.254.169.254`. That's a moderate refactor. | M |
| 10 | **Data deletion and export are manual; privacy policy has gaps** | Rabbit holds other people's health data. "Contact me" deletion doesn't scale, and snapshots now keep deleted data for 14 more days. | `legal.py`: "Ask for a copy or deletion of your data by contacting …". There's no account-delete or export endpoint (only per-item deletes and integration disconnects). The policy says "does not … share it with anyone else", but location and place lookups go to `nominatim.openstreetmap.org` and `open-meteo.com`, and community/social/club features expose some data to other users. The policy doesn't mention retention or backups. | Add `DELETE /app/api/account` (removes `users/<uid>/`, identity, sessions, tokens, push subscriptions; revokes Google, Oura and Garmin tokens) and `GET /app/api/account/export` (a JSON zip of the user's decrypted docs). Update the policy to cover: backups kept for 14 days, the third-party geocoding and weather lookups (coordinates only), what community features make visible, and Anthropic's API data handling. Use the new domain in the policy. | M |
| 11 | **Log retention and size** (check live) | Unbounded journald can fill a 30 GB disk. Logs also hold user IDs and event metadata for an unknown period. | `logs.py` writes JSON to stdout with a redaction filter and no bodies, which is good. No `journald.conf` drop-in in `infra/`. Debian's default cap is 10% of the filesystem (up to 4 GB). | Add `/etc/systemd/journald.conf.d/50-cap.conf`: `SystemMaxUse=500M`, `MaxRetentionSec=30day`. Mention 30-day log retention in the privacy policy. | S |
| 12 | **Rate limiting covers authenticated calls only** | Unauthenticated endpoints (`/authorize`, `/register`, `/token`, `/app/auth/*`) can be hammered, which matters on an e2-micro. | `RateLimiter` (per user, `RATE_LIMIT_PER_MINUTE=30`) wraps tool and app calls. DCR is capped (`MAX_CLIENTS=200`, allowlisted redirects). Caddy has no `rate_limit` (it isn't in the stock build). | Low priority at this scale. Options: Cloudflare in front (`BEHIND_CLOUDFLARE=true` is already supported, with an Origin cert and a firewall limited to CF IPs) and its rate rules, or a per-IP token bucket middleware on the auth routes. | S/M |

## Priority 3: fine / verify occasionally

| # | Item | Status | Evidence / action |
|---|---|---|---|
| 13 | Firewall | Good by design (check live) | `setup.sh`: 80/443 from 0.0.0.0/0 (tag `garmin-mcp-web`) and 22 from the IAP range `35.235.240.0/20` only. `1-setup.sh` passes `DELETE_DEFAULT_SSH=y`. Default-network rules like `default-allow-rdp` may still exist; the audit flags any non-80/443 rule open to the internet. |
| 14 | SSH | Good | OS Login on, `block-project-ssh-keys`, IAP-only, no public 22. Whoever holds `roles/compute.osAdminLogin` is root: keep that to you (and the future deploy SA). |
| 15 | systemd sandboxing | Good | Both units: `ProtectSystem=strict`, `ReadWritePaths` limited to the data dir, `NoNewPrivileges`, empty `CapabilityBoundingSet`, `SystemCallFilter`, `UMask=0077`. Could add `ProtectProc=invisible`, `ProcSubset=pid`, `MemoryDenyWriteExecute=yes` (test first, since cffi/curl_cffi may need W+X), and `IPAddressDeny=` for the metadata server (see item 9). The audit prints `systemd-analyze security` scores. |
| 16 | Secrets handling | Good | Secrets live only in Secret Manager with per-secret bindings to the VM SA. Env files hold `*_SECRET_NAME` only, `0640 root:<svc>`. Cloud Shell scripts read secrets hidden and never echo them. The audit flags any inline secret-looking values. Fernet key rotation isn't supported (a single `Fernet`). To rotate, switch `tokens.py` to `MultiFernet([new, old])` plus a re-encrypt pass. Only needed if a key leaks. |
| 17 | App data at rest | Good | Garmin, TrainingPeaks and Oura tokens, Google Calendar refresh tokens and all Rabbit docs are Fernet-encrypted, written atomically, with 0600 files and 0700 dirs. Garmin tokens are passed inline to `garminconnect` so the library never writes plaintext. The PD is also Google-encrypted. TrainingPeaks uses a browser session cookie, which expires and needs `5-trainingpeaks.sh`. |
| 18 | TLS | Good (check live) | Caddy automatic HTTPS (Let's Encrypt), HSTS 1y, `nosniff`, `X-Frame-Options DENY`, `Referrer-Policy no-referrer`, and no access log because OAuth codes appear in query strings. There's no CSP at the edge. `sslip.io` shares Let's Encrypt rate limits with every other sslip.io user, so the move to `rabbit.holdenottolini.com` fixes that. After the move, update the GitHub, Google and Oura redirect URIs and `PUBLIC_BASE_URL` in both env files. |
| 19 | Dependency pinning | Good, but nothing watches it | `uv.lock` plus `uv sync --frozen`, `bun install --frozen-lockfile`, `garminconnect==0.3.17` pinned, `UV_VERSION` pinned on the VM. Cloud Shell installs uv and bun via unpinned `curl \| sh`. `pip-audit` exists but runs nowhere automatically. Add Dependabot or Renovate plus `pip-audit` and `bun audit` in CI (see item 5). |
| 20 | Cost (check live) | About $0-5/month | e2-micro plus 30 GB pd-standard in us-central1 are in the always-free tier. The in-use external IPv4 is billed (about $3.65/month) unless your free-tier credits cover it. Egress has 1 GB/month free to most regions, so watch photo and attachment downloads. Snapshots run about $0.05/GB-month, and incremental daily snapshots of a few GB used come to under $1/month. The Anthropic API is the real variable cost (item 4). |
| 21 | Release retention | OK | `deploy.sh` keeps 3 releases and supports `--rollback`. Releases are root-owned and not writable by the service. |

## Suggested order

1. Run `10-backups.sh` and `14-offsite-backups.sh`, then `9-audit.sh` (about 10 minutes; the audit fails when either backup is older than 36 h).
2. Run `11-domain.sh`, then `12-harden.sh`: removes the open RDP rule, turns on deletion protection, caps journald, turns off LLMNR, adds uptime checks with an email alert and a monthly GCP budget. Set the Anthropic spend limit by hand.
3. Add `MemoryMax` to garmin-mcp and enable unattended reboot.
4. After the domain move, publish the OAuth consent screen and update the privacy policy.
5. Move deploys to GitHub Actions with WIF, then add account delete and export endpoints.
